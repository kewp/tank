Tank 2007
Revival

A fixed-function OpenGL tank game written for a Core 2 Duo MacBook, nineteen years ago. It builds and runs on Apple Silicon today. Here is what it is, what had to change, and what a browser port would actually cost.

✓ BUILDS macOS 26 / arm64 5,481 lines C++ 13 source files 1 translation unit 17 SGI textures

What it is

A third-person arena shooter. You drive a tank across a 66×127 tile map, trip ambush triggers that spawn wall turrets, collect weapon and health pickups, and eventually wake a boss — a two-part armoured train that rolls in on rails, opens its doors, and fires at you.

No engine, no scene graph, no asset pipeline, no dependency beyond GLUT. Every polygon is a hand-authored vertex table typed into a const GLfloat array. The entire build is one command, because tankmain.cp #includes the other twelve .cp files directly — the whole game is a single translation unit.

The level is ASCII art

The map lives in GLConstants.cp as a literal const int OriginalMap[66 * 127]. Single-letter const int aliases make it readable as a picture while compiling to a plain array of integers. This is the whole level format — there is nothing else.

B wall T tower X floor I H rail A arch R D M pickup 2–9 ambush trigger 

  
Rows 0–7 and 40–52 of the map, commas removed. The 8 running down the left arena is a one-shot trigger: drive over it and five turrets spawn at hard-coded coordinates. Cell 9 wakes the boss.






  
What had to change

  
Less than nineteen years of bit-rot would suggest. The frameworks it needs — GLUT.framework and OpenGL.framework — are deprecated on macOS but still present and functional in the macOS 26 SDK.

  

  

    
ChangeWhy

    
      
-std=c++03The load-bearing flag. ~200 GLfloat vertex-table entries narrow double→float in braced initialisers — legal in C++03, a hard error from C++11 on.

      
sky1.sgi fallbackThe archive is incomplete. The loader wants 16 textures; this one is missing, and the original called exit(1), so the game died before opening a window.

      
drop Carbon.hIncluded in two files, used in neither. A dead Apple-only API blocking non-Apple builds.

      
asset pathsTextures were fopened by bare filename, so it only ran from one working directory.

    
  

  

  
Plus three genuine bugs fixed: the projection aspect ratio was hard-wired to height/height (so 1.0, squashing the scene in any non-square window), glutInitDisplayMode was called after glutCreateWindow where it has no effect, and glEnable(GL_SHADE_MODEL) is not a valid call at all.






  
The one open bug

  

    
Out-of-bounds write · MainGameRoutines.cp:151

    
The trigger-clearing loop uses <= on both bounds. Map holds 8,382 ints; the maximum index computed is 66 + 66×127 = 8,448 — so it reads, and conditionally writes, 264 bytes past the end of the array, every time an ambush fires.

    
It has never visibly crashed because Map is a global and whatever follows it in BSS absorbs the damage. It is still undefined behaviour, and Emscripten's bounds-checked heap will trap on it. The fix is two characters.

  

  
Fifteen other findings — a stale event-queue reset, a missing break that silently grants rapid fire when you wake the boss, an unchecked RLE decoder — are catalogued in docs/FINDINGS.md. Three blockers, six real bugs, six hazards, three minor.






  
Could it run in a browser?

  
Yes, and more easily than the age of the code suggests — because of one fact that dominates everything else: this game has no lighting. Not one glLight*, glMaterial* or glNormal3f call outside glutSolidSphere. Fixed-function lighting is normally the hardest part of an OpenGL 1.x migration, and there is none of it here.

  
What remains is the complete gap list between what the game uses and what WebGL provides:

Why glTexGeni is the real problem — and why it is tractable

  
The game emits zero glTexCoord2f calls. Every texture coordinate in the game is generated by the fixed pipeline: GL_OBJECT_LINEAR for ground and walls, GL_EYE_LINEAR for turrets, GL_SPHERE_MAP for the boss's chrome. None of it exists in WebGL, and it is the specific thing Emscripten's LEGACY_GL_EMULATION is weakest at.

  
The saving grace: the game never sets a custom texgen plane. All planes are OpenGL defaults, so the three modes collapse to simple functions of vertex position and normal — both of which an immediate-mode shim already holds at glVertex3f time. The coordinates can be computed on the CPU inside the shim and handed to WebGL as a plain interleaved buffer. No shader gymnastics, no per-mode variants.

  
Estimated total: 600–900 lines of shim. The recommended route writes it by hand against GLES2 rather than leaning on LEGACY_GL_EMULATION — because the same shim then also delivers modern native rendering on Linux and Windows, and gets macOS off the deprecated frameworks. One rendering path everywhere.


  
Two traps worth naming early

  
Frame timing. The game is fully frame-locked: every duration is seconds × FRAME_RATE, the timer is 1000/80 — integer division, so 12 ms, so 83.3 fps rather than the intended 80. In a browser you get whatever requestAnimationFrame gives you. At 60 Hz the game runs 26% slow; at 120 Hz it runs 44% fast. A fixed-timestep accumulator fixes it while keeping every existing frame-counted constant valid.

  
Texture uploads. There is not a single glGenTextures or glBindTexture in the codebase. Every texture change re-uploads a full 256×256 RGBA image — 15 times per frame, 3.9 MB per frame, ~326 MB/s — to switch between 16 images that never change. Survivable in 2007. Browsers will not tolerate it. This is ~30 lines to fix and is mandatory before WebGL.
